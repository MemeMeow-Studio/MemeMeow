# GIF 上传与压缩

普通图片上传按实际文件内容识别 GIF，原始 GIF 最多 100MB。10MB 和 100MB 分别按 `10 × 1024 × 1024` 和 `100 × 1024 × 1024` 字节计算。其它格式继续使用配置中的单文件上限。单个请求默认最多 128MB，前端按照请求预算分组发送文件。

不超过 10MB 的合法 GIF 保留原始字节。超过 10MB 时使用 gifsicle，依次优化编码、减少颜色，再执行有损优化和尺寸缩放；根据已经生成的文件大小估算缩放比例。每次从原始文件生成结果，最多尝试 11 次。全部帧、每帧显示时间、循环设置和透明背景保留；保存前重新解码并检查动画时间信息和实际文件大小。GIF 处理错误直接成为上传 Task 的终态错误，允许重试的情况仍可由用户显式重试。

GIF 采用处理时间和内存预算：单次处理最多 120 秒，独立进程最多 1GB 地址空间，同一工作区最多两个 GIF 同时处理。单帧仍最多 2500 万像素。GIF 的帧数和累计帧像素由这些处理预算控制。

Docker API 镜像包含 gifsicle。本机运行 API 时需要安装 gifsicle 并使其位于 PATH。临时文件保存在 `MEMEMEOW_DATA_ROOT` 下的 `temp/gif-compression`；未设置环境变量时使用当前工作目录的 `data`。处理结束或超时后清理。服务日志记录每次尝试的输入大小、输出大小、颜色数量、压缩参数和工具错误。

普通上传只登记最终文件。文件指纹、存储用量和后续图片处理使用最终字节。损坏文件、内存超限、超时、工具缺失、编码器错误、动画信息变化和超过目标大小分别返回明确错误码。

合集 ZIP 成员继续按照 manifest 验证原始内容及 SHA，不进行自动压缩。共享 GIF 验证允许超过 100 帧，因此普通上传成功的图片仍能生成缩略图和导出合集。
