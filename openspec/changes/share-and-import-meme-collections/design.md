## Context

当前合集通过 `meme_collections` 和 `meme_collection_items` 保存逻辑成员关系，成员引用稳定 `meme_id`，图片字节仍由 scope-bound `BlobStore` 管理。合集 API 固定使用服务端 `local` scope，项目没有账户或登录系统。现有 `StorageCoordinator` 已提供单张图片的暂存、数据库意图记录、文件落位和恢复流程，图片上传则采用逐文件部分成功语义。

当前生产入口没有资源包导入或 ZIP 导出。历史 Streamlit 资源包只作为格式经验，不能复用其直接 `extractall` 的写入方式。前端 API 客户端统一解析 JSON，因此二进制下载应绕过该封装。

## Goals / Non-Goals

**Goals:**

- 在不新增数据库实体的情况下，让合集 ID 同时成为稳定动态下载地址的一部分。
- 使用一个小型、版本化且可独立校验的 ZIP 格式表达合集名称、成员顺序和图片字节。
- 复用现有图片写入与语境处理能力完成 ZIP 导入。
- 在包结构错误时保持零副作用，在逐图片运行时错误时提供明确的部分成功结果。

**Non-Goals:**

- 不实现认证、分享 token、链接过期、访问统计、权限或分享记录。
- 不保存、缓存或后台预生成 ZIP，也不实现异步导出任务。
- 不实现跨文件系统和数据库的包级全有或全无事务。
- 不导入或导出 embedding、任务、scope、数据库 revision 或旧版 pickle 缓存。
- 不保证与历史 Streamlit 资源包兼容。

## Decisions

### 1. 下载地址直接使用合集稳定 ID

新增 `GET /collections/{collection_id}/export`。端点仍由服务端绑定 `local` scope，不接受 `scope_id` 或 `user_id`。每次请求都重新读取合集及全部成员，不保存分享记录或上次归档，因此同一 URL 自然反映后续成员变化。

选择该方案而不是 token 表，是因为当前产品没有认证和权限模型，合集 ID 已是稳定资源身份，额外分享实体不会提供用户要求的价值。该地址只表达“知道 URL 即可下载”，不承诺保密。

### 2. 先完整生成临时 ZIP，再开始响应

导出服务一次性读取按 `added_at ASC, meme_id ASC` 排序的全部成员，并排除具有 `prepared` 或 `file_applied` 存储操作的 Meme。每张图片通过 `BlobStore.resolve()` 读取并复核数据库记录的大小和 SHA-256。

服务使用标准库 `zipfile` 在受控临时目录生成完整 ZIP，关闭归档成功后才返回 `FileResponse`，并在响应结束后清理临时文件。图片本身已经压缩，归档使用 `ZIP_STORED`，避免为 PNG、JPEG 和 GIF 付出无明显收益的重复压缩成本。

不采用边生成边响应，因为标准 ZIP 中央目录和中途错误会使 HTTP 已返回成功但客户端得到损坏文件。V1 对成员数量和解压总大小设置固定上限；超过限制直接返回稳定错误，不引入任务系统。

### 3. ZIP v1 只携带可移植的必要字段

归档结构固定为：

```text
manifest.json
images/<source_meme_id>.<ext>
```

manifest 使用 UTF-8 JSON，核心结构为：

```json
{
  "format": "mememeow-collection",
  "format_version": 1,
  "collection": {"name": "猫猫合集"},
  "members": [
    {
      "source_meme_id": "uuid",
      "filename_at_export": "疑惑猫.png",
      "path": "images/uuid.png",
      "extension": ".png",
      "size_bytes": 123,
      "sha256": "..."
    }
  ]
}
```

ZIP 内部图片路径使用来源 Meme ID，避免原文件名冲突和路径字符问题。`source_meme_id` 只用于映射导入结果，目标实例始终决定实际 Meme ID。manifest 不携带 AI 语境和 embedding，以保持 v1 格式稳定且避免外部包绕过当前语境校验流程。

### 4. 导入分为全包预检和逐图片提交

新增 `POST /collections/import`，接收单个 multipart ZIP。导入服务先读取中央目录和 manifest，在创建合集前完成以下检查：

- 格式名和版本受支持，manifest 字段类型有效；
- 条目名称为规范相对 POSIX 路径，不包含绝对路径、父目录、NUL、符号链接或重复项；
- manifest 与 `images/` 条目一一对应，没有未声明图片；
- 文件数不超过 500，单图片不超过现有 `max_upload_size`，总解压大小不超过 512 MiB；
- 每张图片的实际大小、SHA-256、扩展名和 Pillow 解码结果与声明一致。

结构预检失败时不创建任何业务数据。预检通过后创建合集，逐项复用现有上传服务和合集成员 repository。该阶段沿用现有上传的部分成功语义：运行时失败不回滚已经完成的图片，但响应必须返回每一项的状态和来源到目标 ID 映射。

不新增包级事务状态机，因为它会要求新的持久化实体、批次可见性和跨重启补偿，超出简单导入需求。若未来产品要求包级原子性，应通过独立 change 设计。

### 5. 文件名冲突只基于当前扁平存储语义处理

导入前对每个 `filename_at_export` 使用现有业务文件名校验：

- 目标文件名不存在：按该名称创建新 Meme；
- 同名文件存在且 SHA-256 相同：复用现有 Meme；
- 同名文件存在但 SHA-256 不同：使用 `<stem>-<sha256前8位><ext>`，若仍冲突则逐步增加哈希前缀长度直到唯一。

不同文件名但相同内容不做全库 SHA 去重，因为当前数据库没有内容唯一约束，静默合并会改变既有 Meme 身份语义。

### 6. 新图片复用普通上传后的处理流程

新建 Meme 仍以 `pending` 状态写入，并为每个成功新建的图片提交常规语境任务。任务提交失败不撤销已经有效的文件、Meme 或合集关系，逐项结果携带可重试错误。导入完成后只失效当前搜索缓存，不从 ZIP 恢复任何向量；使用者通过现有缓存生成流程建立新的 active generation。

### 7. 前端使用原生下载链接和独立 ZIP 上传入口

合集详情增加下载图标按钮和复制链接按钮。下载使用普通 `<a>` 或设置 `window.location`，使浏览器直接处理 `Content-Disposition`，不修改 JSON-only `request()`。

合集列表增加“导入合集”命令，打开单层对话框选择 `.zip` 文件并提交 multipart 请求。结果展示新合集入口以及逐图片成功、复用和失败状态。该入口不复用只接受图片的现有上传 input，避免混合两种文件协议。

## Risks / Trade-offs

- [风险] 合集很大时同步生成 ZIP 占用临时磁盘和请求时间 → 限制最多 500 张、总解压大小 512 MiB，并在响应结束后清理临时文件。
- [风险] 导出期间图片正在重命名或删除导致成员与文件状态不一致 → 下载查询排除活动存储操作，指纹不匹配时整体失败，不返回部分 ZIP。
- [风险] 包结构通过预检后发生磁盘或数据库错误，形成部分导入 → 沿用现有逐文件语义并返回逐项结果，界面不把它显示为全部成功。
- [风险] 合集 ID 下载地址不具备保密性 → 明确这是无认证的公开下载地址；本 change 不把 UUID 当作权限凭据。
- [权衡] 不携带语境 metadata 会要求新图片重新处理 → 换取简单、稳定且不依赖模型版本的包格式。

## Migration Plan

1. 部署后端 ZIP 服务和两个新端点，不需要执行 Alembic migration。
2. 部署前端下载、复制链接和导入入口；旧客户端和现有合集 API 不受影响。
3. 使用当前已有合集验证空合集、正常合集、重名导入和文件冲突。
4. 回滚时移除新端点和前端入口；已经导入的合集和 Meme 均为普通现有数据，无需数据迁移或清理。
